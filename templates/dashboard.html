Record / update a token's device fingerprint (optional · record only, no requests)

The fingerprint is only stored in this dashboard with a format check (android-native / web / unfilled) — it is never sent with any request. Saving an empty value clears it.

When do tokens expire? Unpredictably — DeepSeek's server decides, and there is no way to know in advance. Expired tokens surface as 401 or 503 No tokens available on the client.
Can't tell expired from muted? Press the "Probe tokens" button above — it asks DeepSeek directly for each token's real status (healthy / muted until X / invalidated), no manual testing needed. You can also log into chat.deepseek.com with that account: a re-login prompt = expired; a mute notice when sending = muted; normal chatting = false positive, just press "Restore".
Safe to try: the "Restore" button is always safe — a truly dead token simply re-quarantines automatically, no harm done.

⚠️ Usage model (since Nov 2026): tokens are born on your own device, used on the server.
Since November, upstream revokes whole sessions that get used from a different environment: a token extracted in the browser and pasted into the bridge is treated as session theft and revoked wholesale (rapid bans). So do not extract tokens from the browser — use Method 1 below: run the login tool on your own device and let DeepSeek hand the token directly to you.
Risk disclaimer: whether this model fully avoids bans is unproven — it needs observation time. Please use alt accounts; banned accounts are at your own risk.

Method 1 (recommended) · Log in on your own device: the tool sends one login request identical to the official android app (over your home network) and the token comes straight back in the response — android-born, matching the bridge's shape.

Method A · Desktop (Windows / Mac / Linux, one script)
  1. Install Python (python.org, check "Add to PATH")
  2. Download tools/login_once.py from the repository
  3. Run python login_once.py, follow the prompts (account, password, optional device fingerprint)
  4. Paste the printed token into the form below

Corporate/campus networks and VPNs may get WAF-challenged (the script detects and tells you) — use home broadband or mobile hotspot.

Method B · iPhone / iPad (no computer needed, tested working: Safari login + bookmarklet)

Why not Shortcuts? The old Shortcuts recipe imitated the android app's login, but upstream now requires the login request to carry a device fingerprint produced by the android-native Shumei SDK (an ~89-char string only an android phone can generate). The fingerprint that Safari's web SDK produces is a different format and gets rejected no matter what (RISK_DEVICE_DETECTED). So Shortcuts is retired; the path below was fully tested end to end on a real iPhone on 2026-11-07:

  1. Open chat.deepseek.com in Safari and log in normally with the account and password. First login on a new device asks for email verification: DeepSeek emails you a code, enter it from your mailbox, then the login completes. That's the official flow — just follow it
  2. Once logged in and you can see the chat page, don't close the tab. Tap the share button → "Add Bookmark" and save a bookmark
  3. Open the bookmarks list → "Edit" → tap the bookmark → replace the URL field entirely with this (copy the whole thing, every character):
    javascript:prompt('Your token',JSON.parse(localStorage.getItem('userToken')).value)
    Save
  4. Go back to the chat.deepseek.com tab (you must be on that page) and tap the bookmark. A dialog pops up with your token — select all and copy
  5. Paste the token into the "Paste the token" form below. Done

Notes: step 4 only works while the chat.deepseek.com tab is open; if the dialog shows null or errors, the page isn't logged in (go back to step 1) or JavaScript is disabled (Settings → Safari → Advanced → enable JavaScript). The token comes from a complete official login on your own phone (email OTP included) — it is your account's key, don't share it. Same risk disclaimer as ever: the session is web-born, we can't yet promise it survives the risk wave long-term; use an alt account.

Method C · Android (Termux / HTTP Shortcuts)

Terminal (recommended): install Termux → pkg install curl -y → download tools/deepseek-login.sh → bash deepseek-login.sh.

GUI (alternative): install the open-source HTTP Shortcuts app → Import → from cURL command, paste the curl block from tools/deepseek-login.sh, fill in your account/password (preferably as variables) → home-screen widget.

Device fingerprint (updated 2026-11-07 after real testing: only an android device can produce a valid one)
The real android app carries a Shumei SDK (android-native) device fingerprint (~89-char base64) at login. Same-day full test results:
  • The login request now requires the device_id field — omit it and you get a 422 rejection before the account is even checked
  • Empty / fabricated random values → RISK_DEVICE_DETECTED (biz_code 11)
  • Fingerprints from the browser Shumei SDK (~31-char short ids) are rejected too (11) — including ones taken via desktop Chrome or iPhone Safari. The old "F12 in a browser" recipe is therefore retired
Conclusion: without a physical android device there is no way to produce a fingerprint that passes the check, which is why the panel now recommends the "Safari web login + bookmarklet" path (Method B). Users who do have an android phone can still use Method A: open chat.deepseek.com in the phone's browser (no login), run SMSdk.getDeviceId() in the page console (if it prints undefined, wait a few seconds and run it again), and feed that fingerprint to the login tool.

Paste the token: paste the token printed by the login tool (no quotes). A token equals your DeepSeek account — only paste it into your own dashboard.
The device fingerprint is an optional record: the panel only stores it and checks its format, it never sends it with any request. Fill it if you have a Shumei fingerprint from an android device or the login tool (~89 chars); a short web fingerprint can also be stored (it will be labeled "web format" — known to fail android login, kept for the record).

Token lifetime is unpredictable — when one dies, run the tool again and replace it. The "Probe tokens" button shows each token's real status (healthy / muted until X / invalidated).
